# 15 人软件公司通用 AI 开发框架使用说明

本文面向约 15 人的软件开发公司，说明如何使用 Universal AI Delivery Framework（UAIDF）把 AI 引入日常研发。框架不绑定具体组织架构，也不强制某一种开发方法；它用 `Profiles`、`Skills`、`Harness`、`Loops`、`Gates` 和证据文件，把需求、设计、开发、测试、发布、运维和复盘串成可恢复、可审计、可逐步自动化的工作方式。

适合的团队形态：

- 1-2 名负责人或项目经理
- 1-2 名产品/业务分析人员
- 1 名 UI/体验设计人员
- 3-5 名前端/客户端开发人员
- 3-5 名后端/全栈开发人员
- 1-2 名测试/质量人员
- 1 名 DevOps/运维/发布负责人，可由后端兼任

## 1. 框架核心概念

### 1.1 项目根目录

每个接入 UAIDF 的业务项目，在项目根目录下放置框架治理文件。业务代码仍然放在原来的源码目录里，例如 `src/`、`backend/`、`frontend/`、`apps/`、`packages/`，不需要移动到框架仓库内部。

一个项目接入后的推荐结构如下：

```text
my-project/
  AGENTS.md
  project.yaml
  automation/
    state.json
    acceptance.yaml
    framework-lock.yaml
  docs/
    charter.md
    requirement.md
    adr.md
  evidence/
    gate.yaml
    audit.jsonl
  reports/
    test-report.md
    release-report.md
    metrics-report.md
  checkpoints/
    latest.yaml
  upgrades/
    proposals/
  src/ 或 backend/ 或 frontend/
  tests/
  package.json / pyproject.toml / pom.xml / go.mod 等
```

其中，业务代码和框架治理文件同级。框架负责记录状态、验收、证据、恢复点、路由和升级，不替代原有代码仓库结构。

### 1.2 Profiles

`Profiles` 是项目配置组合，用来描述项目采用什么生命周期、什么技术栈、什么风险策略。

当前框架内置三类 Profile：

- 生命周期：`lifecycle/agile`、`lifecycle/predictive`、`lifecycle/hybrid`
- 技术栈：`technology/typescript`、`technology/python`、`technology/django-vue`
- 风险策略：`risk/accelerated`、`risk/balanced`、`risk/conservative`

项目初始化后，这些选择会写入 `project.yaml` 和 `automation/framework-lock.yaml`。

### 1.3 Skills

`Skills` 是 AI 和人员执行任务时要遵守的动作规范。框架把技能分成两类。

角色技能：

- `roles/value`：价值责任，负责业务目标、范围取舍、验收优先级。
- `roles/experience`：体验责任，负责用户旅程、界面状态、可用性和可访问性。
- `roles/technology`：技术责任，负责架构、实现、接口、数据库、依赖、可维护性。
- `roles/quality`：质量责任，负责验收矩阵、测试证据、发布门禁、风险判断。

任务技能：

- `tasks/clarify-requirement`：澄清需求。
- `tasks/tdd`：测试驱动开发。
- `tasks/debug`：系统化调试。
- `tasks/design-review`：设计评审。
- `tasks/code-review`：代码评审。
- `tasks/release`：发布准备。
- `tasks/retrospective`：复盘。

一个真实任务通常由一个角色技能加一个任务技能组成。例如“开发登录功能”通常需要 `roles/value` 确认验收目标，`roles/technology` 负责实现，`roles/quality` 负责验收，执行时使用 `tasks/tdd`。

### 1.4 Harness

`Harness` 是执行护栏，主要包括：

- `harness/prompts/system-constraints.md`：AI 工作的系统约束。
- `harness/prompts/task-contract.md`：每个任务开始前必须明确的任务契约。
- `harness/prompts/review-rubric.md`：代码和方案评审顺序。
- `harness/policies/data-policy.yaml`：数据分级规则。
- `harness/policies/permissions.yaml`：权限和审批规则。
- `harness/policies/logging.yaml`：日志脱敏和保留规则。
- `harness/policies/resume.yaml`：中断恢复规则。

### 1.5 Loops

`Loops` 是带预算和停止条件的工作循环：

- `discovery`：需求发现循环，最多 4 轮，适合需求不清晰时使用。
- `delivery`：交付循环，最多 4 轮，适合实现已确认需求。
- `verification`：验证循环，最多 5 轮，适合证据缺失或门禁未通过时使用。
- `operations`：运营/事故循环，最多 6 轮，适合线上问题。
- `framework-improvement`：框架改进循环，最多 3 轮，适合沉淀流程和能力升级。

### 1.6 Gates

门禁是项目阶段和证据检查点：

| Gate | 名称 | 重点 |
| --- | --- | --- |
| `G0` | opportunity | 机会、目标、价值假设 |
| `G1` | requirements | 需求、验收标准、范围 |
| `G2` | design | 设计、架构、风险、回滚 |
| `G3` | implementation | 实现、测试、代码评审 |
| `G4` | release | 发布、回滚、监控 |
| `G5` | operations | 运行、事故、可靠性 |
| `G6` | learning | 复盘、指标、框架改进 |

门禁判断只接受四种验收状态：

- `PASS`
- `FAIL`
- `BLOCKED`
- `NOT_VERIFIED`

不得把 mock 证据当作 staging 或 production 证据。

## 2. 如何创建新项目

### 2.1 安装并验证框架

在 UAIDF 框架仓库根目录执行：

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -e '.[test]'
bash scripts/verify-framework.sh
```

验证通过后，命令行中会有 `uaidf` 命令。

### 2.2 初始化一个新项目

假设要创建一个 TypeScript/Vue 敏捷项目：

```bash
python -m uaidf init \
  --name my-project \
  --target ../my-project \
  --profile lifecycle/agile \
  --profile technology/typescript \
  --profile risk/balanced
```

命令会在 `../my-project` 中生成：

- `project.yaml`
- `AGENTS.md`
- `automation/state.json`
- `automation/acceptance.yaml`
- `automation/framework-lock.yaml`
- `docs/`
- `reports/`
- `evidence/`
- `checkpoints/`

初始化不会自动生成业务代码。你可以之后创建前端、后端、测试和部署目录。

### 2.3 新项目第一天要补齐的内容

初始化完成后，建议先补齐以下文件：

`docs/charter.md`：

- 项目背景
- 目标用户
- 业务目标
- 最小可交付版本
- 非目标范围
- 关键风险
- 负责人和替补

`docs/requirement.md`：

- 需求列表
- 用户故事或业务流程
- 验收标准
- 边界场景
- 权限和数据要求
- 依赖系统

`docs/adr.md`：

- 技术选型
- 架构决策
- 数据库和接口设计
- 第三方依赖
- 可观测性
- 回滚策略

`automation/acceptance.yaml`：

```yaml
schema_version: 1
requirements:
  - id: REQ-001
    title: 用户可以登录系统
    status: NOT_VERIFIED
    evidence: []
  - id: REQ-002
    title: 管理员可以查看用户列表
    status: NOT_VERIFIED
    evidence: []
```

`evidence/gate.yaml`：

```yaml
schema_version: 1
evidence:
  - id: REQ-001-local-test
    kind: local
    status: PASS
    path: reports/test-report.md
    notes: 登录接口单元测试和前端表单交互测试通过
    verified_at: "2026-06-17T10:00:00Z"
```

### 2.4 第一次通过门禁

检查门禁：

```bash
python -m uaidf gate-check --project ../my-project G0
```

如果通过，推进状态：

```bash
python -m uaidf transition --project ../my-project G0 --actor "project-owner"
```

如果失败，通常原因是 `automation/acceptance.yaml` 中有需求没有 `PASS` 状态，或者缺少证据路径。

### 2.5 每次阶段性完成后创建恢复点

```bash
python -m uaidf checkpoint \
  --project ../my-project \
  --objective "完成登录功能的本地验证" \
  --next-action "补齐发布前验收证据"
```

之后如果 AI 会话、机器或人员交接中断，先执行：

```bash
python -m uaidf resume-check --project ../my-project
```

只有结果是 `RESUMED` 才能自动继续。若结果是 `WAITING_CONFIRMATION`，需要人工确认输入、授权、风险和代码状态是否变化。

## 3. 如何在原有项目上继续开发

### 3.1 原有项目代码放到什么位置

原有项目代码不需要移动到 UAIDF 框架仓库里。推荐做法是在原有项目仓库根目录直接初始化框架治理文件。

例如已有项目目录：

```text
crm-system/
  backend/
  frontend/
  tests/
  docker-compose.yml
  README.md
```

接入 UAIDF 后变成：

```text
crm-system/
  AGENTS.md
  project.yaml
  automation/
  docs/
  evidence/
  reports/
  checkpoints/
  backend/
  frontend/
  tests/
  docker-compose.yml
  README.md
```

也就是说，`backend/`、`frontend/`、`tests/` 等原有业务目录继续留在原位置，框架文件放在项目根目录同级。

### 3.2 给原有项目初始化框架

进入 UAIDF 框架仓库，执行：

```bash
python -m uaidf init \
  --name crm-system \
  --target ../crm-system \
  --profile lifecycle/hybrid \
  --profile technology/django-vue \
  --profile risk/conservative
```

默认情况下，如果目标项目已有手写的 `AGENTS.md`，初始化逻辑不会覆盖它。若确实要覆盖生成文件，才使用 `--force`：

```bash
python -m uaidf init \
  --name crm-system \
  --target ../crm-system \
  --profile lifecycle/hybrid \
  --profile technology/django-vue \
  --profile risk/conservative \
  --force
```

使用 `--force` 前应先备份或评审已有规则。

### 3.3 原有项目接入时的清点步骤

第一步，盘点项目现状：

- 技术栈：前端、后端、数据库、消息队列、部署环境。
- 生命周期：敏捷迭代、瀑布交付、混合模式。
- 风险等级：是否涉及客户数据、财务数据、生产系统、监管数据。
- 测试基础：单元测试、接口测试、E2E、手工测试、CI。
- 发布方式：手工发布、CI/CD、灰度、回滚。

第二步，补齐 `project.yaml`：

```yaml
schema_version: 1
project:
  name: crm-system
  description: 内部 CRM 系统持续迭代
lifecycle: hybrid
technology:
  - django-vue
risk_profile: conservative
autonomy:
  level: supervised
  requires_approval: true
```

第三步，补齐 `automation/acceptance.yaml`：

把已有需求、缺陷、技术债拆成可验收条目。每个条目至少要有：

- `id`
- `title`
- `status`
- `evidence`

第四步，补齐 `docs/adr.md`：

原有项目最容易出现“大家脑子里知道，但 AI 不知道”的隐性约束。至少记录：

- 目录结构
- 本地启动命令
- 测试命令
- 数据库迁移规则
- API 约定
- 权限模型
- 禁止改动的历史兼容点
- 发布和回滚方式

第五步，首次验证：

```bash
python -m uaidf validate --schema project.schema.json ../crm-system/project.yaml
python -m uaidf resume-check --project ../crm-system
python -m uaidf gate-check --project ../crm-system G0
```

若 `resume-check` 不是 `RESUMED`，先确认当前状态和下一步动作，再继续开发。

### 3.4 原有项目继续开发的日常流程

每天开始前：

1. 读取 `automation/state.json`。
2. 读取 `automation/acceptance.yaml`。
3. 读取 `state.json` 中 `last_report` 指向的报告。
4. 确认当前 Gate、下一步动作和阻塞项。
5. 如果是中断恢复，先执行 `python -m uaidf resume-check --project <project>`。

每个需求开始前：

1. 产品或负责人用 `tasks/clarify-requirement` 澄清目标、范围和验收。
2. 技术负责人用 `roles/technology` 判断是否需要 ADR。
3. 质量负责人用 `roles/quality` 把验收标准映射到证据。
4. 开发人员用 `tasks/tdd` 写失败测试，再实现。
5. 代码完成后用 `tasks/code-review` 做评审。
6. 发布前用 `tasks/release` 检查发布、回滚和监控证据。

## 4. 框架中需要哪些人员参与

UAIDF 不要求公司新增固定岗位，而是要求每个责任有人承担、有人备份。15 人团队可以按下面方式分配。

### 4.1 管理者或公司负责人

对应责任：框架采用决策、风险授权、资源协调。

主要工作：

- 决定公司默认使用哪些生命周期和风险策略。
- 指定四类责任的主责和替补：价值、体验、技术、质量。
- 批准高风险动作：生产发布、生产数据操作、密钥创建或轮换、策略覆盖、框架升级。
- 每 30/60/90/180 天检查采用进度。
- 不用 AI 调用量评价个人绩效，只把它作为成本和诊断指标。

产出文件：

- `assessments/capability-matrix.yaml`
- `reports/metrics-report.md`
- 框架升级审批记录

### 4.2 项目负责人或项目经理

对应责任：跨角色协调、Gate 推进、风险闭环。

主要工作：

- 维护 `automation/state.json` 中当前阶段、阻塞项和下一步动作。
- 组织每日任务契约确认。
- 确认每个任务有主责、验收证据、验证命令和恢复规则。
- 在门禁通过后执行 `transition`。
- 中断恢复时组织确认。

常用命令：

```bash
python -m uaidf gate-check --project <project> G1
python -m uaidf transition --project <project> G1 --actor "project-manager"
python -m uaidf checkpoint --project <project> --objective "<目标>" --next-action "<下一步>"
```

### 4.3 产品经理或业务分析人员

对应技能：`roles/value`、`tasks/clarify-requirement`。

主要工作：

- 明确用户、业务目标和最小可交付范围。
- 把模糊需求转成可测试验收标准。
- 管理需求优先级和范围取舍。
- 不允许没有价值假设和验收证据的任务进入开发。

产出文件：

- `docs/charter.md`
- `docs/requirement.md`
- `automation/acceptance.yaml`

### 4.4 UI/体验设计人员

对应技能：`roles/experience`、`tasks/design-review`。

主要工作：

- 梳理用户旅程。
- 覆盖正常态、空态、错误态、权限态、恢复态。
- 检查界面文案、布局、一致性和可访问性。
- 在实现前参与设计评审。
- 在验收时提供体验证据。

产出文件：

- 设计说明或原型链接
- `docs/requirement.md` 中的体验验收标准
- `reports/design-review.md`，如项目需要

### 4.5 技术负责人或架构负责人

对应技能：`roles/technology`、`tasks/design-review`、`tasks/code-review`。

主要工作：

- 读取现有架构、代码契约、测试和运行约束。
- 选择满足正确性、可观测性、回滚需求的最小设计。
- 对框架、依赖、API、数据库、迁移方案写 ADR。
- 审查 AI 生成代码是否破坏架构边界。
- 对高风险技术变更要求人工确认。

产出文件：

- `docs/adr.md`
- API 契约
- 数据库迁移说明
- 代码评审结论

### 4.6 前端/客户端开发人员

对应技能：`roles/experience`、`roles/technology`、`tasks/tdd`、`tasks/debug`。

主要工作：

- 根据验收标准实现界面和交互。
- 开发前确认状态覆盖：正常、加载、空、错误、权限、恢复。
- 为组件、页面流程和关键交互补测试。
- 记录本地验证证据，不把手工看过当作自动测试通过。
- 涉及用户数据或敏感日志时先做数据分级。

常见验证：

```bash
npm test
npm run lint
npm run build
```

### 4.7 后端/全栈开发人员

对应技能：`roles/technology`、`roles/quality`、`tasks/tdd`、`tasks/debug`。

主要工作：

- 根据验收标准实现 API、服务、任务、数据库改动。
- 用 TDD 或回归测试证明行为变化。
- 数据库迁移必须有回滚策略。
- 接口、权限、审计、日志不得泄漏秘密或个人敏感数据。
- 生产配置、数据迁移、密钥操作必须人工审批。

常见验证：

```bash
python -m pytest
ruff check .
python -m uaidf route-check --data-class internal --task code
```

### 4.8 测试/质量负责人

对应技能：`roles/quality`、`tasks/code-review`、`tasks/release`。

主要工作：

- 把每条验收标准映射到自动或手工证据。
- 维护 `automation/acceptance.yaml`。
- 维护 `evidence/` 和 `reports/`。
- 用 `PASS`、`FAIL`、`BLOCKED`、`NOT_VERIFIED` 判断门禁，不凭感觉放行。
- 发布前确认测试、回滚、监控和数据路由证据。

产出文件：

- `reports/test-report.md`
- `reports/release-report.md`
- `evidence/gate.yaml`

### 4.9 DevOps/运维/发布负责人

对应技能：`tasks/release`、`tasks/debug`、`operations` loop。

主要工作：

- 管理 CI/CD、环境、部署和回滚。
- 维护发布计划、回滚触发条件和监控指标。
- 事故发生后进入 `operations` loop。
- 保存脱敏日志和事故证据。
- 事故关闭后参与复盘。

产出文件：

- 发布记录
- 回滚方案
- 事故报告
- 运维证据

## 5. 不同类型开发项目如何配置文件

### 5.1 敏捷互联网产品或 SaaS 项目

适合场景：

- 快速迭代
- 需求会持续变化
- 中低风险业务系统
- Web 前端、后台管理、SaaS 产品

推荐 Profile：

```yaml
lifecycle: agile
technology:
  - typescript
risk_profile: balanced
autonomy:
  level: supervised
  requires_approval: true
```

初始化命令：

```bash
python -m uaidf init \
  --name saas-admin \
  --target ../saas-admin \
  --profile lifecycle/agile \
  --profile technology/typescript \
  --profile risk/balanced
```

重点配置：

- `automation/acceptance.yaml`：按用户故事维护验收矩阵。
- `docs/requirement.md`：记录每个迭代的用户流程和边界场景。
- `docs/adr.md`：记录前端状态管理、API 契约、权限模型。
- `reports/test-report.md`：记录单元测试、组件测试、E2E 结果。

建议节奏：

- 每个需求走 `discovery -> delivery -> verification`。
- 每周运行一次 `metrics-report` 和 `retrospective`。
- 发布前必须有 `release` 技能检查。

### 5.2 政企、合同制或交付型项目

适合场景：

- 合同范围明确
- 阶段验收严格
- 需求变更需要审批
- 客户现场或私有化部署

推荐 Profile：

```yaml
lifecycle: predictive
technology:
  - django-vue
risk_profile: conservative
autonomy:
  level: supervised
  requires_approval: true
```

初始化命令：

```bash
python -m uaidf init \
  --name government-delivery \
  --target ../government-delivery \
  --profile lifecycle/predictive \
  --profile technology/django-vue \
  --profile risk/conservative
```

重点配置：

- `docs/charter.md`：合同范围、验收边界、里程碑。
- `docs/requirement.md`：需求规格和变更记录。
- `automation/acceptance.yaml`：按合同条款、功能模块、测试用例建立证据。
- `evidence/gate.yaml`：区分 local、staging、production 和 manual 证据。
- `harness/policies/data-policy.yaml`：确认 confidential/restricted 数据处理方式。

建议节奏：

- `G0-G4` 使用严格阶段门禁。
- 每次需求变更必须先走 `tasks/clarify-requirement`。
- 高风险设计必须走 `tasks/design-review`。
- 发布前必须有回滚负责人、触发条件和客户沟通路径。

### 5.3 老系统维护和二次开发项目

适合场景：

- 历史系统缺少文档
- 测试覆盖不足
- 需求多来自线上问题和客户反馈
- 改一处容易影响多处

推荐 Profile：

```yaml
lifecycle: hybrid
technology:
  - python
risk_profile: conservative
autonomy:
  level: supervised
  requires_approval: true
```

若是 Django + Vue 老系统：

```yaml
lifecycle: hybrid
technology:
  - django-vue
risk_profile: conservative
autonomy:
  level: supervised
  requires_approval: true
```

重点配置：

- `docs/adr.md`：先记录现有架构和禁止破坏的兼容点。
- `automation/acceptance.yaml`：先覆盖当前变更，不要求一次补全全部历史需求。
- `checkpoints/`：每次安全小步修改后创建恢复点。
- `reports/test-report.md`：记录新补的回归测试。

建议节奏：

- 每个 bug 先走 `tasks/debug`，复现和定位后再改代码。
- 每个修复至少补一条回归证据。
- 涉及数据库、权限、账务、生产数据时必须人工确认。

### 5.4 AI 功能或模型集成项目

适合场景：

- 在产品中接入大模型、智能客服、代码生成、文档生成、推荐等能力
- 存在数据分级和模型路由问题
- 需要评估输出质量和安全边界

推荐 Profile：

```yaml
lifecycle: agile
technology:
  - python
risk_profile: conservative
autonomy:
  level: supervised
  requires_approval: true
```

重点配置：

- `framework/defaults/model-routing.yaml` 或项目自定义路由文件。
- `harness/policies/data-policy.yaml`：明确 public、internal、confidential、restricted。
- `harness/policies/logging.yaml`：禁止记录 secrets、tokens、passwords、credentials。
- `automation/acceptance.yaml`：增加 AI 输出质量、安全、拒答、人工接管、审计证据。

路由检查示例：

```bash
python -m uaidf route-check --data-class public --task analysis
python -m uaidf route-check --data-class internal --task code
python -m uaidf route-check --data-class restricted --task analysis
```

默认策略下：

- `public` 和 `internal` 可走 `enterprise-cloud`。
- `confidential` 需要 private 或 local 路由。
- `restricted` 默认拒绝，除非项目通过审批切换到 approved private/local。

### 5.5 生产运维、事故修复和热修项目

适合场景：

- 线上缺陷
- 生产事故
- 紧急回滚
- 数据修复

推荐 Profile：

```yaml
lifecycle: hybrid
risk_profile: conservative
autonomy:
  level: supervised
  requires_approval: true
```

重点配置：

- `automation/state.json`：记录当前事故阶段、阻塞项和下一步动作。
- `evidence/`：保存脱敏日志、复现结果、修复验证、回滚检查。
- `reports/incident-report.md`：记录根因、影响、处理过程、后续动作。
- `reports/retrospective.md`：事故关闭后复盘。

建议节奏：

1. 分级事故严重程度和数据等级。
2. 保存证据并脱敏。
3. 进入 `operations` loop。
4. 复现或定位后再改代码。
5. 修复后补回归证据。
6. 关闭前确认回滚、监控和复盘动作。

## 6. 不同岗位如何高效使用提示词和配置

### 6.1 通用任务提示词结构

任何岗位使用 AI 前，都建议把提示词拆成四段：

```text
请遵守项目 AGENTS.md、project.yaml 和当前 Gate。

任务目标：
<要完成什么>

上下文：
<需求、代码路径、设计文档、当前状态、风险约束>

任务契约：
- 输入和假设：
- 使用的 Profile：
- 需要的角色技能：
- 需要的任务技能：
- 验收证据：
- 验证命令：
- 中断恢复规则：

输出要求：
<需要 AI 输出什么，例如需求文档、测试计划、代码修改、评审结论>
```

如果任务涉及实现或修复，应明确要求：

```text
请先写最小失败测试，确认失败原因符合预期，再实现最小改动，最后运行相关测试并记录验证证据。
```

如果任务涉及评审，应明确要求：

```text
请按需求和门禁符合性、正确性和回归风险、安全和数据权限、测试证据、可维护性和运维就绪度的顺序评审。
```

### 6.2 管理者提示词

用途：制定采用计划、检查风险、审阅指标。

示例：

```text
你是 15 人软件公司的 AI 研发治理顾问。请基于以下项目状态，检查当前是否符合 UAIDF 的 M1 到 M2 成熟度升级条件。

输入：

- automation/state.json：
- automation/acceptance.yaml：
- reports/metrics-report.md：
- assessments/capability-matrix.yaml：

2. 阻塞项
3. 30 天内最小改进行动
4. 哪些动作需要管理层批准
5. 不要用 AI 调用量评价个人绩效
```

高效配置：

- 每个项目必须有 `risk_profile`。
- 每个责任必须有主责和替补。
- 每周至少查看一次 `metrics-report` 和 `retrospective`。

### 6.3 产品经理提示词

用途：把需求变成可验收范围。

示例：

```text

业务想法：
<粘贴原始需求>

1. 已确认事实
2. 假设
3. 开放问题
4. 不做范围
5. 最小可交付版本
6. 可测试验收标准
7. 建议写入 automation/acceptance.yaml 的 requirements 条目

```

高效配置：

- 在 `automation/acceptance.yaml` 中用稳定 ID 管理验收项，例如 `REQ-001`。

## 7. 数据分级和模型路由

框架默认数据分级：

| 数据等级 | 含义 | 默认处理 |
| --- | --- | --- |
| `public` | 可对外分享的信息 | 可走 enterprise-cloud |
| `internal` | 公司内部代码和工作产物，不含敏感/秘密/监管内容 | 可走 enterprise-cloud |
| `confidential` | 客户、财务、安全或敏感业务内容 | 需要 private-cloud 或 local |
| `restricted` | 密钥、凭据、受监管个人数据、支付数据、生产事故证据 | 默认拒绝 |

默认路由文件是 `framework/defaults/model-routing.yaml`。

检查路由：

```bash
python -m uaidf route-check --data-class internal --task code
```

如果要处理 confidential 或 restricted 数据，不要直接把内容发给外部模型。应先做以下动作：

1. 脱敏或抽象化输入。
2. 使用 private-cloud 或 local 路由。
3. 记录项目风险决策。
4. 明确日志不保存 secrets、token、password、credential、authorization。
5. 必要时由管理者或安全负责人审批。

## 8. 门禁、证据和报告怎么维护

### 8.1 `automation/state.json`

记录当前项目状态：

```json
{
  "schema_version": 1,
  "current_stage": "G0",
  "stage_status": "IN_PROGRESS",
  "confirmed_gates": [],
  "completed_requirements": [],
  "blocked_items": [],
  "last_verification_at": null,
  "last_report": null,
  "next_action": "complete G0 opportunity and charter"
}
```

项目负责人每天先看这个文件。

### 8.2 `automation/acceptance.yaml`

记录需求验收矩阵。门禁检查要求所有 requirements 都是 `PASS`，且每条都有 evidence。

建议格式：

```yaml
schema_version: 1
requirements:
  - id: REQ-001
    title: 用户可以通过手机号登录
    status: PASS
    evidence:
      - evidence/login-local-test.yaml
  - id: REQ-002
    title: 登录失败时显示错误原因
    status: NOT_VERIFIED
    evidence: []
```

### 8.3 `evidence/`

保存证据。证据类型只能是：

- `local`
- `mock`
- `staging`
- `production`
- `manual`

示例：

```yaml
schema_version: 1
evidence:
  - id: login-local-unit-test
    kind: local
    status: PASS
    path: reports/test-report.md
    notes: pytest tests/test_login.py -q 通过
    verified_at: "2026-06-17T10:00:00Z"
```

### 8.4 `reports/`

建议保存：

- `test-report.md`
- `release-report.md`
- `metrics-report.md`
- `incident-report.md`
- `retrospective.md`
- `design-review.md`

生成指标报告：

```bash
python -m uaidf metrics-report --project <project> --output <project>/reports/metrics-report.md
```

指标包括：

- 流动效率
- 质量
- 可靠性
- 价值
- 能力
- 成本

注意：AI 调用量只作为成本和诊断，不作为个人绩效。

## 9. 框架升级和公司持续改进

当团队发现某个流程、模板、技能、路由或门禁需要改进时，不要直接改所有项目。应走框架升级流程：

1. 创建升级提案，说明负责人、原因、预期效果、风险和迁移范围。
2. 方案确认后才能试点。
3. 运行 dry-run，保护项目覆盖配置。
4. 执行确认后才能 apply。
5. 应用后验证。
6. 准备 rollback。

常用命令：

```bash
python -m uaidf upgrade propose --project <project> --file <proposal.yaml>
python -m uaidf upgrade confirm-solution --project <project> --id <upgrade-id> --actor "<actor>"
python -m uaidf upgrade dry-run --project <project> --migration 0.1.0-to-0.2.0
python -m uaidf upgrade confirm-execution --project <project> --id <upgrade-id> --actor "<actor>"
python -m uaidf upgrade apply --project <project> --migration 0.1.0-to-0.2.0
python -m uaidf upgrade rollback --project <project> --migration 0.1.0-to-0.2.0
```

禁止：

- 未确认方案就试点。
- 未确认执行就迁移。
- 为了让任务看起来完成而绕过门禁。
- 删除核心规则或降低质量检查。

## 10. 建议的 30/60/90/180 天落地路线

### 30 天：完成第一个试点

目标：

- 选一个低到中风险项目。
- 用 `uaidf init` 初始化项目。
- 指定 value、experience、technology、quality 四类责任主责和替补。
- 建立 `automation/acceptance.yaml` 和第一批证据。
- 完成一次门禁检查和 checkpoint。

验收：

- 项目有 `project.yaml`、`AGENTS.md`、`automation/state.json`、`automation/acceptance.yaml`。
- 至少一个需求从 `NOT_VERIFIED` 到 `PASS`。
- 团队知道如何中断恢复。

### 60 天：扩展到两个项目

目标：

- 一个新项目，一个老项目。
- 固化日常协作 Playbook。
- 每周运行 `metrics-report` 和复盘。
- 发布流程使用 `tasks/release`。

验收：

- 两个项目都能使用 Profiles、Skills、Harness、Loops。
- 有 release、incident、retrospective 的实际记录。
- 能力矩阵中有培训计划。

### 90 天：形成组织级配置能力

目标：

- 能根据项目类型切换 `agile`、`predictive`、`hybrid`。
- 能根据技术栈切换 `typescript`、`python`、`django-vue`。
- 默认模型路由上线。
- restricted 数据策略完成演练。

验收：

- confidential/restricted 数据不会误发外部模型。
- 门禁和证据成为项目管理默认动作。
- 高风险动作有审批记录。

### 180 天：进入持续改进

目标：

- 框架升级机制常态化。
- 复盘能产生框架升级提案。
- 低风险工作可在监督下更高程度自动化。
- 能力成熟度达到 M3，部分团队达到 M4。

验收：

- 定期生成 metrics report。
- 有 upgrade dry-run、apply、rollback 证据。
- AI 辅助开发从个人技巧变成组织能力。

## 11. 常见错误和纠正方式

| 错误 | 风险 | 纠正方式 |
| --- | --- | --- |
| 只买 AI 工具，不改验收门禁 | 产出多但质量不可控 | 先建立 `acceptance.yaml` 和证据门禁 |
| 原有项目代码搬到框架仓库里 | 破坏项目结构和 Git 历史 | 在原项目根目录初始化框架文件 |
| 没有 checkpoint | 中断后无法安全恢复 | 阶段性完成后运行 `uaidf checkpoint` |
| mock 证据当生产证据 | 发布风险被低估 | 在 `evidence` 中区分 kind |
| 需求没验收标准就让 AI 写代码 | 返工和误实现 | 先用 `tasks/clarify-requirement` |
| AI 直接处理密钥或生产日志 | 泄漏风险 | 使用数据分级、脱敏和 route-check |
| 代码评审只看风格 | 漏掉正确性和安全问题 | 使用 `review-rubric.md` 的评审顺序 |
| 用 AI 调用量评价个人 | 鼓励刷量和错误优化 | 只用于成本和诊断 |
| 未确认就升级框架 | 多项目被错误规则影响 | 使用 confirmed upgrade 流程 |

## 13. 推荐的团队工作节奏

每天：

- 项目负责人读 `state.json`、`acceptance.yaml`、`last_report`。
- 产品确认需求是否清晰。
- 开发按 TDD 或调试流程小步推进。
- 测试更新证据状态。
- AI 任务必须有任务契约。

每周：

- 运行一次指标报告。
- 做一次简短复盘。
- 更新能力矩阵。
- 检查是否有流程改进值得进入 framework-improvement loop。

每次发布前：

- 验收矩阵全部必要项为 `PASS`。
- 证据区分 local、staging、production、manual。
- 发布负责人和回滚负责人明确。
- 监控和回滚触发条件明确。
- 高风险动作获得审批。

每次事故后：

- 保留脱敏证据。
- 记录根因和修复。
- 补回归测试。
- 更新复盘动作。
- 判断是否需要框架升级提案。

## 14. 一句话原则

UAIDF 的核心不是让 AI 更自由，而是让团队把“目标、责任、证据、权限、恢复、复盘”写清楚，然后让 AI 在清楚的边界内更快、更稳地完成工作。
